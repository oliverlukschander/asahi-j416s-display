# 0123: send the Thunderbolt DP IN role bit

Direct continuation of 0122 after its first hardware test.

## What 0122's result showed

0122 correctly split the ACIO wake from the crossbar select (confirmed: the wake
fires right after `Activate`, no crossbar reselect at that exact moment). But the
observed outcome was, if anything, slightly different from 0119/0121 in the wrong
direction: DCP didn't even reach `INACTIVE_SINK_DETECTED` this time before the DPRX
timeout. Investigating further found a second, pre-existing "reselect dpin after
nub" step (`USB4: reselect dpin after nub: %d`, already in `dcp_dptx_connect()`,
unrelated to tonight's Activate/DidChangeLinkConfig work) that reselects the
crossbar unconditionally right after `request_display` succeeds -- independent of
`Activate`'s own crossbar handling either way.

The important observation across all three of tonight's ordering variants (0119,
0121, 0122): **every one of them reached the identical final outcome** (either
`INACTIVE_SINK_DETECTED` then DPRX timeout, or straight to DPRX timeout) despite
meaningfully different Activate/crossbar sequencing each time. That consistency,
across genuinely different orderings, points at a signal we are not sending at all,
not a timing detail we can fix by further reordering on our end.

## The missing signal

The reference implementation (aurora-silicon/linux#8) packs a "role" bit into the
attributes field of both `validate_connection` (AFK method 12) and `connect` (AFK
method 11): bit 0 = 0 for a direct PHY connection, 1 for a Thunderbolt/USB4 DP IN
tunnel route. This is *separate* from `supportsHPD` (bit 8) -- 0118's speculative
change to `supportsHPD` was already reverted in 0121 because the reference
implementation never touches it for a tunnel route; this role bit is the actual,
previously-unidentified signal that does distinguish the two cases. Our own
analog-DPIN path has never set it, in any candidate this entire project -- every
prior test sent a plain, direct-PHY-shaped attributes value (`0x100`) even though
this has always been a genuinely USB4-tunneled connection.

Hypothesis: DCP firmware's tolerance for a failed/inconclusive AUX probe may depend
on this bit -- a Thunderbolt tunnel's AUX proxying is a fundamentally different,
possibly slower or differently-timed path than a direct PHY's AUX pins, and DCP may
need to be told which kind of connection this is to decide whether to keep training
past `INACTIVE_SINK_DETECTED` rather than giving up.

## The fix (kernel commit 44de38a)

Both `dptxport_validate_connection()` and `dptxport_connect()` now OR in
`dcp_is_usb4_output(service->ep->dcp) ? 1 : 0` alongside their existing fields --
`dcp_is_usb4_output()` is this driver's existing, already-correct equivalent of the
reference implementation's dedicated `dptx_tunnel` flag for exactly this connection.
`validate_connection`'s reply check is relaxed to match the reference
implementation's own tolerance: only the role bit is allowed to differ between what
we sent and what DCP echoes back (any other mismatch still fails validation as
before). `dptxport_connect()` already tolerated a mismatched reply unconditionally
(a pre-existing `dev_notice`-only check), so no change was needed there.

## Test plan

Same protocol, single boot. Watch for `DPTX validate target=... ` and `DPTX connect
target=...` log lines: the `unk`/attrs values logged should now include the role
bit (e.g. connect's logged `unk=0x101` instead of `0x100`). Then watch specifically
whether `INACTIVE_SINK_DETECTED` is followed this time by `SET_LINK_RATE` -- the
concrete signal this hypothesis is correct -- rather than silence until the DPRX
timeout.
