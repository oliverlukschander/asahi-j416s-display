# T602x DPIN mux programming — 2026-09-21

Stock `apple_dpxbar_set_t602x()` never looked at the mux index. It always
wrote `state<<20` and `state<<8` into `T602X_REG_030` (DPPHY select) and
ATC bit `0x100` (`ATC_DPPHY`). Logs saying `Switched dpin0 to dispext0,0`
were software tracking only. Analog stayed on the Type-C PHY (USB4) or,
when DPTX targeted phy 3, the empty HDMI jack.

t8103/t6000 already program:

| Mux | MUX_CTRL fields | ATC bit |
| --- | --- | --- |
| dpphy | bits 23:20 and 11:8 | `BIT(8)` |
| dpin0 | bits 15:12 and 3:0 | `BIT(0)` |
| dpin1 | bits 19:16 and 7:4 | `BIT(4)` |

The T602x path now uses that same field layout at `T602X_REG_030` / `0x034`
and dumps 0x000–0x070 on every switch.

DPTX side, in the same boot:

- Prefer USB-C `dcpext1` (`315c00000.dcp`) over HDMI `dcpext0`.
- Remote-port ATC is the Type-C index (Right = 2). HDMI phy 3 is not used.
- Encode DPIN in bits 13:12 (`dpin0=1`).
- `atcphy` is NULL for USB4 so APCALLs do not start HDMI or the USB4 ATC.
- No HPD kick after `INACTIVE_SINK`. No dpin/target-OR cycling.

ice3186's `{die,atc,dpin,core}` model is the DPTX remote-port identity.
T602x DPIN analog was the missing half: the crossbar has to actually
enable `ATC_DPIN0` onto adapter `0:5`.

Success: `SET_ACTIVE_LANE_COUNT` with lanes>0, DP IN `DPRX=1`, Hyprland
sees the VMM7100 besides `eDP-1`.
