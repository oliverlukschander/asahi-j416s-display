# Diagnostic 0090 boot result and SDDM ordering — 2026-09-21

The planned reboot ran after Oliver confirmed ready. The first boot
(1c91ba5e60974628a3259c4796f54d30) left the internal screen unusable.
Oliver forced shutdown; the journal records the SMC forced-shutdown event.
The second boot (320edefca258477d9c882452d1cdb100) restored the display.
Both boot the diagnostic 0090 driver: both contain its new read_edt_data logs.
The hub was unplugged. No additional module load or parameter experiment ran.

The logs strongly support a compositor/DRM startup-order race:

| Event | Black-screen boot | Successful boot |
| --- | --- | --- |
| Hyprland welcome | 11.860632 s | 21.286927 s |
| Apple DRM registered | 12.135010 s | 21.224025 s |
| Panel modeset | absent in saved kernel log | 21.537224 s |

In the failed boot, the panel DCP nevertheless booted and supplied six modes
at 9.953423 s. No panel kernel panic or DCP crash was found. This does not
prove the exact compositor-side failure: its detailed previous /run log is
lost after reboot. It does identify a concrete startup ordering defect and
means the USB4 code is not established as the cause of the black screen.

Both external controllers request just:
`read_edt_data key=initial-vbi-advance-lines count=1 default0=0x2 ret=0`.
No external timing-table request appears through that callback. It is not
an observed route for supplying EDID or TimingElements. The no-timing warning
also appears with both external connectors disconnected.

## Startup mitigation

scripts/wait-apple-drm.py waits up to 30 seconds for an apple-drm card with a
connected eDP-1, nonempty modes, and an existing character device. It does not
assume card2, open the DRM node, modeset, access MMIO, or alter kernel state.
It only reads sysfs attributes and file metadata. Failure logs a clear message
and prevents SDDM from launching prematurely. SDDM's existing retry policy
remains in effect. The drop-in sets TimeoutStartSec=45s.

Six tests cover missing devices, dynamic numbering, wrong driver, missing
modes, disconnected panel, and timeout/delayed availability. All pass.
A real-system check returns `Apple DRM ready: card2, eDP-1 connected with modes`.
The sandbox hides /dev/dri, so the live check required execution outside it.
No claim is made that the next boot has been validated yet.

Installation targets:
- /usr/local/libexec/j416s-wait-apple-drm
- /etc/systemd/system/sddm.service.d/20-apple-drm-ready.conf

Only systemctl daemon-reload follows installation. No SDDM restart and no
reboot: the current desktop is left running. This mitigation is separate
from the USB4 link problem, which remains unresolved.
