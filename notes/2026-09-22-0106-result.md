## New evidence: the DP-IN hop counter is nonzero

```
# offset relative_offset counter_id value      (host route0-0 port5)
0x0000    0 0x00 0x0000421b
0x0001    1 0x00 0x00000000
0x0002    2 0x00 0x00000000
```

Counter index0 on the DP video path's DP-IN hop (route0-0 port5) reads
0x0000421b (16923) after the sequence above -- nonzero, where
`tb_path_activate()` clears it to0 at every path activation. This counter
was enabled for the first time this boot by the0106`dp_video_counter=1`
gate; nothing else in this driver ever turns it on for a DP tunnel, so a
nonzero value here is new, direct hardware evidence that traffic did leave
the crossbar/DP IN adapter into the USB4 fabric on this exact attempt --
not merely that firmware/DCP reported success.

The hub-side read (route0-1 port19, the DP OUT-adjacent hop) was also taken
for comparison:

```
# offset relative_offset counter_id value      (hub route0-1 port19)
0x0000    0 0x00 0x00000000
```

This reads0, but0106 never set`in_counter_index`on that hop -- only on the
DP-IN side (see notes/2026-09-22-0106-dp-video-counter.md, "single
checkpoint... deferred rather than combined"). An unenabled counter reading
zero proves nothing, exactly the caveat this whole diagnostic exists to
avoid; this reading is not evidence the hub side received nothing, it is
simply uninstrumented. No conclusion is drawn from it.

## What this does and does not establish

Established: the DCP/crossbar/DP-IN boundary is not silently failing to
emit -- packets are demonstrably entering the tunnel on the host side. This
narrows the fault: it is no longer defensible to keep suspecting crossbar
internals (034,gate ordering,clock sequencing) as the primary open question,
since the one thing those internals were suspected of preventing (video
actually leaving DP IN) demonstrably happens.

Not established: where between "left DP IN" and "reached the monitor" the
signal is lost. That could be the tunnel itself, the hub's DP OUT
programming, the physical VMM7100/HDMI retimer, or the cable/monitor side.
The natural next checkpoint is the symmetric one deferred from this
candidate: enable the same counter mechanism on the hub-side hop (the video
path's last hop, in_port = hub upstream port) to see whether that traffic
crosses into the hub's side of the tunnel at all.
