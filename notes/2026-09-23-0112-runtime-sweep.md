# 0112: make the DPIN0 mode-value sweep reboot-free

Oliver flagged that reboot cycles are the real cost driver for this
project's progress and asked for a way to test the bounded mode-value
sweep (see 2026-09-22-0110-mode-value-guess.md, -0110-result.md,
2026-09-23-0111-mode-value-lower-bound.md, -0111-result.md) without a
full reinstall+reboot per value.

## Why every prior candidate needed a reboot

Two independent reasons, both fixed here:

1. `MODE_VALUE` was a compile-time `#define`. Changing it required
   editing the header, rebuilding `thunderbolt_apple.ko`, reinstalling,
   rebuilding the initramfs, and rebooting to load the new module.
2. Even if the value were runtime-adjustable, the handshake itself
   wasn't safely re-testable within one boot: MODE_B's write is a pure
   OR and MODE_A's write only ever sets one bit on top of whatever was
   there; a second activate without a genuine register reset in
   between would land on top of the first attempt's leftover bits
   instead of a clean value, invalidating the isolation between test
   values. There was also a latent one-shot latch
   (`acio->dpin_attempted`) in `apple_usb4_right_dpin0_set_active()`
   that would silently return `-EALREADY` on any activate after the
   first, for the rest of the boot -- so even a register-clean retry
   would never have actually run.

## What changed

`drivers/thunderbolt/apple-dpin-handshake.h`:
- `apple_dpin_handshake()` now takes `mode_value` as a parameter
  instead of reading the removed `APPLE_DPIN_MODE_VALUE` macro. Out-of-
  range values (`> APPLE_DPIN_MODE_VALUE_MAX`, 15) are rejected with
  `-EINVAL` before any register access at all -- a sysfs typo fails
  loud and inert, not silently.
- New deactivate-path clear: bounded to exactly the bits any in-range
  `mode_value` write could have set (MODE_A bits 0-15, MODE_B bits
  7-10), nothing outside that range. This is explicitly NOT a claim
  about native's teardown behavior (never traced, same caveat as the
  existing HPD-on-deactivate precedent) -- it exists solely so this
  driver's own next activate on the same boot starts from a state it
  can reason about.

`drivers/thunderbolt/apple.c`:
- New `dpin_mode_value` module parameter, `0644`, default 8 (0111's
  last clean-but-inconclusive value). Read fresh on every activate via
  `sysfs`: `/sys/module/thunderbolt_apple/parameters/dpin_mode_value`.
- `apple_usb4_right_dpin0_set_active()`: resets `acio->dpin_attempted =
  false` after a successful deactivate, so a later activate this boot
  is actually reachable instead of latching `-EALREADY` forever.

## New workflow after this candidate is installed and booted once

No more reboots for further values in this sweep. To test a value:

```
echo N | sudo tee /sys/module/thunderbolt_apple/parameters/dpin_mode_value
```

...then plug the hub into the right port, capture, check for a
picture, unplug. The deactivate that runs on unplug leaves clean state
for the next value. Remaining untested bound: secondary_bit=2,
`dpin_mode_value=10`.

## Validation

`scripts/test-dpin-handshake.c`: updated for the new signature; added
(a) out-of-range rejection with zero register access, (b) the actual
round-trip this candidate exists for -- activate value 9, clean
deactivate, activate value 10, assert no bit contamination between them
(this assertion is only satisfiable if the deactivate genuinely left
MODE_A/MODE_B clean) -- and (c) confirmation that the deactivate clear
never touches bits outside its documented range (tested with
adversarial high-bit-set fixtures). ASan/UBSan, 13 scenarios, all
passing.

`make` in `src/thunderbolt` rebuilds only `apple.o`/`thunderbolt_apple.ko`
(this candidate touches `apple.c` in addition to the header, unlike
0110/0111, but still only this one translation unit). SHA256 confirms
every other module unchanged from 0111:

## Safety scope

Same DPIN0 resource (`0xf01e50000`, size `0x4000`) this driver has
safely read and written since 0093; no new addresses, no ACIO analog
register, no lpdptxphy, no forbidden register. This candidate itself
still needs one reboot to load (module parameters and code paths can't
be hot-patched into an already-loaded module); every value sweep after
that should not.
