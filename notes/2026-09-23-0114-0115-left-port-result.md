# First live test of 0114+0115 combined: left port, still no picture

This is the first time 0114's request_display resend has actually run
on real hardware (the planned right-port-only test of 0114 alone was
never carried out before Oliver relocated), and the first test of
0115's port generalization. Hub + Synaptics adapter + BenQ monitor on
the LEFT USB-C port, boot at 18:57 (`journalctl -k -b`).

## What worked

- 0115's port generalization is confirmed correct on real hardware,
  not just by device-tree inspection: the ACIO that came up is
  `701ac0000.cio` (typec_index 0, left port) and the crossbar that
  logged `native DPIN0: route selected` is `70304c000.mux` -- the
  left-port addresses computed by `apple_usb4_typec_acio_base()` and
  `apple_dpxbar_is_typec_crossbar()`, not the old hardcoded right-port
  ones. The whole native-DPIN0 mechanism now genuinely runs on a port
  it was never built for, no module option needed.
- The native DPIN0 handshake itself still succeeds:
  `native DPIN0: active=1 base=0x0000000701e50000, CONTROL=0x0c
  ACK=0x10 mode_value=8` then `active=1 handshake=0`, and DCP accepts
  it: `native DPIN0: DCP active=1 result=0`.
- 0114's resend line fires exactly as designed:
  `USB4: resend request_display after native DPIN0 activate: -110`.

## What's still broken

- That resend result is `-110` (`-ETIMEDOUT`). The plain
  `USB4: analog DPIN request_display core=1 atc=0: -110` line logs the
  same code from the underlying call.
  `dptxport_request_display()` is timing out, not failing outright --
  DCP never answers within the AFK call's timeout window.
- 12 seconds later: `DPRX timeout, keeping DP tunnel`. The DisplayPort
  receiver in the Synaptics adapter never completed AUX/DPRX
  negotiation. This matches the very first log lines for this boot:
  `DP IN analog: leaving PHY alone until DPRX timeout` and
  `DP IN armed typec0; DPTX HPD in 200 ms (no PHY connect)` -- the
  "analog DPIN mux" path this project built only arms the crossbar/mux
  routing; it was never going to itself drive DPTX link training, that
  was always expected to come from DCP once `request_display`
  succeeds. It didn't.
- DRM never saw a connected external connector this boot at all
  (`card2-USB-1/2/3` all stayed `disconnected` in sysfs), and
  `hyprctl monitors` shows only `eDP-1`. Confirms the failure is
  upstream of DRM even noticing a mode -- consistent with the timeout,
  not a new/different failure mode.
- Oliver confirmed visually: monitor remains in standby.

## Why this is still useful information

Before this boot, the working hypothesis (from the XNU power-state
trace, see `notes/2026-09-23-xnu-power-state-trace.md`) was that our
driver never resends `request_display` at all, unlike real macOS's
`setPowerState`-driven resend. That specific gap is now closed by 0114
and it did not fix the picture -- the resend *fires* but *times out*.
That relocates the real blocker: whatever precondition DCP is waiting
for before it will answer `request_display` successfully is still not
satisfied at the moment we resend, even though our own native DPIN0
handshake reports success on our side of the link.

This matches the two already-identified, not-yet-decompiled next
avenues from the XNU trace: `setPowerState`'s `powerstate == 0`
(deactivate) path, and whatever XNU-side code actually sets the
`_displayRequested` flag that gates a successful `request_display` in
the first place (our resend today assumed activation success was
sufficient to set an equivalent flag; the timeout says it is not, or
something else the real driver does in between is still missing).
